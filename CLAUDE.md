# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page static dashboard (Thai UI) tracking the Rubber Authority of Thailand (กยท.) FY2569 action plan. Everything — HTML, CSS, JS — lives in one file, `index.html`. No build, no package manager, no tests; libraries come from cdnjs (only Chart.js loads upfront; SheetJS is loaded via `loadScriptOnce()` when the Excel button is clicked; ExcelJS, html2canvas, jsPDF are lazy-loaded via the `LIBS` map when a report is generated). Viewers open it from a monthly LINE alert, mostly in LINE's in-app browser on phones, so first-load speed matters — don't add blocking scripts to `<head>`.

The user's constraint: nothing may be installed — keep it a plain static file deployable on Vercel, and talk to Supabase with plain `fetch` against the REST API (no supabase-js, no npm).

## Data flow

```
Google Sheet "Data ACP69" --(Apps Script, on menu click)--> Supabase public.sheet_snapshots <--(anon key, read-only)-- index.html
```

- Staff edit the Google Sheet. The bound Apps Script (local file `AppScript`, pasted into the Sheet's script editor by the user) pushes every sheet in `SYNC_SHEETS` to Supabase when the user runs **📁 เมนูระบบ > บันทึกผลการดำเนินงานย้อนหลัง** (`runArchiveProcess` calls `syncToSupabaseLogged` at the end) or **ส่งข้อมูลขึ้นเว็บ (Supabase) เดี๋ยวนี้**. Results are appended to the `ประวัติการบันทึก` sheet.
- `supabase/schema.sql` defines the single table: one row per sheet, `headers` (ordered array) + `rows` (array of arrays of display strings, i.e. what `getDisplayValues()` returns — same as the old gviz CSV export). All sheets are sent in one upsert, so the dashboard never sees a half-updated set. RLS: `select` for anon/authenticated only; writes need the service_role / `sb_secret_` key, stored only in the Apps Script's Script Properties (`SUPABASE_SECRET_KEY`).
- Don't store emails or other personal data in `sheet_snapshots` — the anon key is public, so anyone can read the table.
- Visitor stats: an inline script at the top of `<head>` (which also defines `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `requestSnapshots()` and starts `earlySnapshotsRequest` so data downloads in parallel with Chart.js/fonts) calls `rpc/log_page_view` after `load`. The function is `security definer`; anon has no direct access to `page_views`, and the `page_view_monthly` / `page_view_daily` views are `security_invoker`, so stats are visible only inside Supabase. Only a random per-device id (localStorage `acp-visitor`), source (`?src=` or LINE user agent) and an is-mobile flag are stored.
- LINE OA (menu 🚨 in `AppScript`, broadcast to every follower, so each send uses quota): `sendAlertNow` sends one carousel built by `buildMonthlyMessage`. It has a summary card (`buildSummaryBubble`: project count, budget, disbursement, mean plan % with blanks counted as 0, completed projects, count per status level) and the Early Warning card (`buildRiskBubble`); the risk card is left out when no project is at risk. `getRiskProjects()` computes both with the dashboard's rules: FY2569 status = the status on the row that supplies the plan % (fallback: worst row), and Trigger Point for FY ≥ 2570. Its counts must match the dashboard's (verified Nov 2026: 81/19/5/16). `sendYearEndNow` sends a year-end card from the `ผลสิ้นปีงบประมาณ` sheet (`getYearEndSummary`). Per a user decision (Nov 2026), `yearEndSendBlock(fy)` allows sending only from FY `YE_LINE_FROM_FY` = 2570, and only from `YE_LINE_DAY` = 15 Oct after that fiscal year ends on 30 Sep; the preview still shows the card. `previewLineCards` shows the JSON for LINE Flex Message Simulator without sending. Card buttons open `DASHBOARD_URL?src=line` and `…#lineorg`. Followers are both executives and unit staff, so cards stay organisation-wide (no per-unit broadcasts).
- `indexAppScript` is a separate Apps Script HTML page (Early Warning / LINE alerts), not part of the Vercel site. `AppScript` also references dialog files (`ArchiveDialog`, `CancelDialog`) that exist only in the Apps Script project.

## Source of truth: `Note`

The user edits the dashboard in the local file `Note` (git-ignored). `index.html` is a straight copy of it: when `Note` changes, `cp Note index.html`, then commit and push. Make dashboard edits in `Note` and copy; don't let the two diverge.

## Run / deploy

- Preview: open `index.html` in a browser. It needs network access to Supabase and cdnjs.
- Deploy: Vercel, Framework Preset **Other**, empty build command and output directory; pushing to `main` redeploys. `vercel.json` only sets headers (`X-Robots-Tag: noindex, nofollow`, `nosniff`, `no-referrer`) and `cleanUrls`. If a CSP is ever added, it must allow cdnjs, Google Fonts and `*.supabase.co`.
- No Node/Python on this machine. To smoke-test JS, run headless Chrome (`chrome.exe --headless=new --dump-dom file:///…`) and read the console via `--enable-logging=stderr`.

## Architecture of `index.html`

Several `<script>` blocks, in order:
1. View switching (`activateView`) for the left nav. Each view has a hash link (`#strategy`, `#kpi`, `#annual`, `#masterplan`, `#lineorg`, `#dgarea`; the main page has none) that `activateView` writes with `history.replaceState` and `activateViewFromHash()` reads on load and on `hashchange`. `#method` opens `#methodModal` after `loadAndRender()` finishes (`window.__openMethodOnLoad`). LINE rich-menu buttons and the LINE cards use these links, so don't rename view ids. The views: `view-dashboard`, `view-strategy` (menu "ผลการดำเนินงานตามยุทธศาสตร์", renamed from ความเชื่อมโยงยุทธศาสตร์ Nov 2026; see below), `view-kpi` (ผลการดำเนินงานตามตัวชี้วัดที่สำคัญ, see below), `view-annual`, `view-masterplan`, `view-lineorg` (menu "ความก้าวหน้าแผนปฏิบัติการตามสายงาน", renamed Nov 2026: executive cards `#dgAreaCards` + per-project table `#dgDrilldownPanel`), `view-dgarea` (PA/MOU lists only). Both of the last two are filled by `renderDgAreaView()` via element ids, so moving markup between sections needs no JS change. In `view-lineorg`, `renderDgDrilldown()` shows unit buttons (`#dgUnitChips`) for the selected line, from the global `lineUnits(label, projects)`: units from the `ส่วนงานภายใต้ผู้บริหาร` sheet (`window.ACP_EXEC_UNITS[label]`, built in the loader) plus any project `owner` not listed there, sorted by project count desc (ties keep sheet order). Units with no projects show as disabled dashed buttons. Matching uses `normOwner()`. Report topics mirror the menu (numbered 1–6 in menu order), preceded by the unnumbered `exec` ("สรุปผู้บริหาร", always one A4 page: a single html block so paginate never splits it, plus Excel sheet `สรุปผู้บริหาร`; keep it under the page body height, about 649px, when adding content): `strategy` ("2. ผลการดำเนินงานตามยุทธศาสตร์"; Excel sheet `ยุทธศาสตร์-KPI`), `lineorg` ("5. ความก้าวหน้าแผนปฏิบัติการตามสายงาน": line summary, per-line unit summary from `R.byDg[i].units` (also built with `lineUnits`), one project table per unit; Excel sheet `สายงาน`) and `dgarea` ("6. ความก้าวหน้า PA และ MOU"; Excel sheet `PA-MOU`).
2. Report generator IIFE (PDF/Excel, A4 landscape): picks fiscal year + month from current data or the history sheet; topics in `TOPICS`.
3. `window.ACPDash` — rendering module; `ACPDash.start({records, strategies, orgKpis, historyPeriods, masterPlans})` draws everything.
4. Loader (last block): `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SHEET_SPECS`, then `loadAndRender()` → `fetchSheetBySpec()` per sheet → `buildDashboardData()` / `buildOrgKpis()` / `buildHistoryDataset()` → `ACPDash.start()`. Errors show `#errorOverlay`.

Loader behaviours worth knowing:
- `loadSnapshots()` fetches all rows of `sheet_snapshots` once. `fetchSheetRows(name)` rebuilds `{header: value}` objects plus `__fields` (column order), the same shape Papa.parse used to produce, so the `build*` functions are unchanged. Column order matters: the `ส่วนงานภายใต้ผู้บริหาร` matrix uses `__fields[0]` as the owner column and the rest as executives.
- In `ส่วนงานภายใต้ผู้บริหาร`, only headers matching `ผวก|ผู้ว่าการ` are executive columns (`execCols`). The columns `ตามคำสั่งการยางแห่งประเทศไทย ที่` / `เรื่อง` / `ลงวันที่` (found by `คำสั่ง` / `^เรื่อง` / `ลงวันที่`) become `window.ACP_EXEC_ORDERS`. Orders change often, so the sheet keeps every order with a checkbox column (header `ใช้อยู่`/`ปัจจุบัน`/`ยึด`/`มีผล`, or no header) marking the one in force: only checked orders are shown; if none is checked, every filled order is shown, shown as the หมายเหตุ `#dgOrderNote` under `#dgAreaCards` (user request, Nov 2026). An optional `ปีงบ` column (any column except A) splits the mapping and orders per fiscal year into `window.ACP_EXEC_BY_FY` (blank year = fallback); `execFor(fy)` picks that year, else the latest year ≤ fy, else the blank-year rows. Live records use `execFor(LIVE_FISCAL_YEAR)`; `projectsForPeriod()` maps history owners with `execFor(per.fiscalYear)`, and the header period switch (`show()`) and report `prepare()` swap `ACP_EXEC_UNITS`/`ACP_EXEC_ORDERS` to that year, so past years keep their old line structure when a new order arrives (user request, Nov 2026).
- `fetchHistorySheetRaw()` returns raw arrays (no header row); `buildHistoryDataset()` reads `ผลการดำเนินงานย้อนหลัง` by column position A–T (layout written by the Apps Script archive; N–P are ARRAYFORMULA columns in the sheet).
- Each `SHEET_SPECS` entry lists alternate sheet names and `required` headers; a missing sheet yields an empty array and is skipped if `optional`. Keep sheet names in sync with `SYNC_SHEETS` in `AppScript`.
- Only the latest `Fiscal_Year` found in the projects sheet is kept.
- KPI results (`view-kpi`, hash `#kpi`, report topic `kpi` "7. ผลการดำเนินงานตามตัวชี้วัดที่สำคัญ", Excel sheet `ตัวชี้วัด`; added Nov 2026): sheet `ผลตัวชี้วัดที่สำคัญ` (in `SYNC_SHEETS`, `SHEET_SPECS.kpiResult`, all fiscal years kept) → `buildKpiResults()` → `window.ACP_KPI_RESULTS` (one record per KPI per `ปีงบ` per round. The sheet has one row per KPI per year with per-round columns (user layout Nov 2026): headers containing `ไตรมาส N` (e.g. `คาดการณ์ไตรมาส1`, `ผลการดำเนินงานไตรมาส 3`) or `สิ้นปี`; un-numbered `หมายเหตุ`/`สถานะ`/`คิดเป็นร้อยละ` belong to the nearest round to their left, so parsing is positional (`fetchSheetRows` adds `__raw` because `หมายเหตุ` repeats). A legacy `รอบรายงาน` column (one row per round) still works. `kpiResultList(fy, period)` defaults to the latest round, used by the strategy chips and the PDF; Excel lists every round. Quarter rounds: cumulative result meeting the annual target = บรรลุ, else the round forecast of the year-end result decides `คาดว่าบรรลุ` (`KR_LIKELY`) / `เสี่ยงไม่บรรลุ` (`KR_RISK`); result only = `อยู่ระหว่างดำเนินการ`; the year round keeps บรรลุ/ไม่บรรลุ/รอผล; `KPI_Strategy_Code` blank = org-level row). Columns are found by header name; if `ค่าเป้าหมาย`/`หน่วยนับ` are swapped (number in the unit column) they are swapped back. `pct` = result ÷ target, or target ÷ result when `ทิศทาง` says น้อยกว่าดี (no column: name contains "ไม่เกิน"); with no result it uses `ค่าคาดการณ์` (`isForecast`, drawn faded). `status` = the sheet `สถานะ` if filled (บรรลุ/ไม่บรรลุ/รอ…), else result vs target → `บรรลุเป้าหมาย`/`ไม่บรรลุเป้าหมาย`, no result → `รอผล`. Summaries count KPIs per status and never average % across KPIs (different units; user agreed Nov 2026). Org KPIs that are also annual KPIs (e.g. KPI-ST69-03/04/11) are not duplicated as rows: the org row lists them in `ตัวชี้วัดรายปีที่ใช้ผลเดียวกัน`, and `kpiResultFor(code, fy)` resolves those aliases. `renderKpiView()` (called after `ACPDash.start`) draws cards, per-strategy tables (`kpiResultGroups`) and a year trend for org KPIs when > 1 year exists. `view-strategy` shows `kpiResultChip()` under each org/annual KPI target for `__viewFY`. Org KPI targets on that page and in report topic `strategy` come from `orgTargetText(o, fy)`: the yearly target in `ผลตัวชี้วัดที่สำคัญ` for that fiscal year, falling back to `ตัวชี้วัดองค์กร` (which holds the end-of-plan 2570 targets; user decision Nov 2026, not shown).
- 5-year enterprise plan panel (`#krPlanPanel` in `view-kpi`, added Nov 2026; also in report topic `kpi`: PDF tables after the KPI tables and Excel sheet `แผน 5 ปี`, all built from the shared `plan5Data()`): sheet `เป้าหมาย 5 ปี` (`SHEET_SPECS.plan5`, in `SYNC_SHEETS`) → `buildPlan5()` → `window.ACP_PLAN5` ({startYear, endYear from the `เป้าหมายสิ้นปี 25xx` header, items}). Yearly rows in `ผลตัวชี้วัดที่สำคัญ` link to it through the `ลำดับในแผน` column (`k.plan`), a stable number from the plan file (1, 2, 3, 4, 5.1 gross profit 2566–68, 5.2 net profit 2569–70, 1.1 … 4.3), because KPI-STyy codes change every year. `renderPlan5()` shows each year (full-year round, else latest round), the cumulative result per `วิธีนับผล 5 ปี` (`สะสม` = sum of yearly results, `เฉลี่ย`, else latest; a year with no actual result uses its forecast, marked *, so it matches the plan file — user choice Nov 2026) and % of the 5-year target. Per user decision: follow the plan file `ตัวชี้วัดองค์กร.xlsx` (sheet `KPI 66-70`); a target of 0 in the file means the KPI did not exist that year (row omitted); KPI 1.1 uses ร้อยละ (12.5) with the rai figure in หมายเหตุ; gross profit uses org code KPI-ORG-06 so it never merges with net profit KPI-ORG-05 in the trend.
- Strategy linkage (`view-strategy`, report topic `strategy`): `buildStrategyLinks()` in the loader builds `window.ACP_LINKS` once from live-FY sheets; `buildStrategyTree(projects)` groups any period's projects as ยุทธศาสตร์ → ตัวชี้วัดองค์กร → กลยุทธ์/ตัวชี้วัดรายปี → โครงการ and returns project lists only (the dashboard aggregates with `hProg`/`hStat`/`SCH`, the report with `aggTree` → `aggGroup`). Project → annual KPI comes from `ตัวชี้วัดโครงการ.KPI_Year_Code` (fallback `เชื่อมโยงโครงการ`). Annual KPI → initiative/org KPI/strategy comes from `เชื่อมโยงตัวชี้วัด` and `ตัวชี้วัดรายปี`. Annual KPI codes are unique across years, so `ตัวชี้วัดรายปี` is a lookup with no FY filter. `เชื่อมโยงโครงการ.KPI_Org_Code` is a per-project "ตอบตัวชี้วัดองค์กรโดยตรง" flag (mostly NON-KPI-ORG, and it disagrees with the hierarchy), so it is shown only as a tag (`ACP_LINKS.prjOrg`) and never used for grouping. Without the new sheets the page shows codes instead of names. Progress shown is the mean of the linked projects, not real KPI results (the KPI sheets hold targets only); the page and the report say so. Master plans carry `cbe` from `แผนแม่บท.CBE_Code` (`.cbe-tag`, names from `Core_Business_Enabler`).
- Cancelled projects: if any row of a project in `โครงการ` has `สถานะโครงการ` containing "ยกเลิก", `buildDashboardData()` drops the project from `records` (so it's excluded from every stat, chart and history view via `window.ACP_CANCELLED`) and pushes its details (name, owner, budget, `เหตุผลการยกเลิก`) to `window.ACP_CANCELLED_LIST`. The 5th card on the main dashboard (`#cancelledCard`, opens `#cancelModal`) shows that list. Some project codes appear on several rows of the projects sheet.
- `#kpiGrid` alone has 5 cards: 5 columns at ≥1440px, 3+2 at 1001–1439px, then the shared `.kpi-grid` rules (2 columns with the 5th card full-width, 1 column ≤380px). Other `.kpi-grid`s stay at 4 columns.
- `normCode()` re-pads numeric project codes to 6 digits (e.g. `010101`), since leading zeros get lost in Sheets.
- `isYes()` interprets checkbox-like cells (TRUE/Yes/✓/ใช่…).
- Status levels are Thai strings: `['ดีมาก','ดี','พอใช้','ต้องปรับปรุง']` (FY2569 and earlier, taken from the sheet).
- Trigger Point (FY ≥ `TP_FROM_FY` = 2570, user decision Nov 2026, source: `Trigger_Point_ติดตามแผนปฏิบัติการ 2570.xlsx`): the dashboard computes the status itself in `applyTriggerPoint(projects, fy)` and ignores the sheet's status columns. `status_plan` = `tpLevel(progress_cum)`, `status_pct_cum` = `tpLevel(progress_pct_cum)`, `status` = the worse of the two (`tpWorst`, never an average). Levels: ≥90% `ปกติ`, 70–<90% `เฝ้าระวัง`, <70% `วิกฤต`. Everything that names levels, colours, card/chart labels or bar bands goes through `statusScheme(fy)` → `STATUS_SCHEMES.sheet` / `.tp` (dashboard: `SCH`, chips via `setStatusChips`; report module: lazy `sch()` set in `prepare()`), so a period is judged by its own fiscal year. The Apps Script LINE alert (`getRiskProjects`) has a copy of `TP_FROM_FY` / `tpLevel` / `tpWorst`; keep the two in sync. The `#methodModal` documents both schemes.
- Annual completion ("โครงการที่บรรลุเป้าหมายทั้งปี"): a project is `สำเร็จ` only if **every** KPI row has `สถานะโครงการ (ผลเทียบเป้าทั้งปี)` = `สำเร็จ` (history: column P). The user confirmed this rule (Oct 2026) — don't switch to averages/majority. Projects with some KPIs done are counted as `อยู่ระหว่างดำเนินการ`.
- Project-level % for multi-KPI projects: `progress_year` (จากเป้าหมายทั้งปี) = **mean** of the KPIs (user confirmed Oct 2026); `progress_pct_cum` (จากเป้าหมายสะสม) = **mean** of the KPIs too (user changed it from worst-KPI/min in Nov 2026; the "riskiest KPI" note under the bar was removed). This applies to live data (`buildDashboardData`), history (`buildHistoryDataset`), Trigger Point's target dimension and the Apps Script LINE alert. `status_pct_cum` for FY2569 is still the sheet status of the worst KPI. `progress_cum` (เทียบแผนสะสม) = the project-level value repeated on every KPI row (first non-empty). Per-KPI annual % in the sheet tops out at 100%, so the mean only reaches 100% when every KPI does — consistent with the completion rule.
- Year-end close: the Apps Script menu **ปิดปีงบประมาณ** (`closeFiscalYear` → `buildYearEndRows`) writes one row per project of the latest `Fiscal_Year` to the sheet `ผลสิ้นปีงบประมาณ` (`ผลสิ้นปี` = `บรรลุเป้าหมาย` / `ไม่บรรลุเป้าหมาย` / `ยกเลิก`, same rule as above) and syncs it. In `index.html`, `buildYearEnd()` → `window.ACP_YEAR_END[fy]`. For a closed year, `projectsForPeriod()` takes name/owner/strategy/cancelled from that year's rows (not from the current year's project list), and the **final** period (`กันยายน`, or live data while the live year is the closed year, per `isYearEndPeriod()`) gets `applyYearEnd()`: `completion` stays `'สำเร็จ'` for passed projects (so existing counters work) and becomes `'ไม่บรรลุเป้าหมาย'` otherwise. `window.__yearEndFY` switches the dashboard's completion texts; reports use `R.yearEnd` / `R.L_DONE` / `R.L_REST`.
- Fixing data after a period was archived or the year was closed: edit the sheet, then rerun **ปิดปีงบประมาณ** (it overwrites the same year and syncs; never after FY+1 rows exist in `โครงการ`). For a history period, use the menu **บันทึกผลย้อนหลังใหม่ (เลือกเดือน)** (`rearchivePeriodMenu` → `archiveSnapshot(fy, month, {onlyFY:true})`): the user types FY and month, rows of that period are replaced from the current results sheet (only that FY's rows), and it syncs. It refuses periods after the current report month. The normal archive (`runArchiveProcess`) always takes the month before *today*, so it must not be used for a past period (in November it would write ตุลาคม of the next FY).
- In that year-end period the **headline** metric everywhere is the annual one (user decision, Oct 2026): use `headProgress(p, ye)` (= `progress_year` at year-end, else `progress_cum`), `headStatus(p, ye)` (= `บรรลุ/ไม่บรรลุเป้าหมาย`, else the ผลเทียบแผนสะสม status) and `headLabels(ye)` for column titles. `renderDashboard` exposes `YE_MODE` / `hProg` / `hStat` / `HL`; the report module has `YE` (set in `prepare()` before `computeReport`) with `hP` / `hS` / `T(normal, yearEnd)`. The status donut becomes annual-% bands (`yearPctBandCounts`, same thresholds as `pctColorClass`). Tables that already show both % columns keep both and only switch the status badge.

## Header badge, title, share card

- The header badge's main line is the data cut-off date "ข้อมูล ณ <date>" (user decision Nov 2026: option 2, no sheet column). `liveAsOfDate(fy, ACP_SYNCED_AT)` = last day of the month before the sync, capped at 30 Sep of the data's fiscal year. History periods use `monthAsOfDate(fy, monthName)` = end of that month; `periodAsOf(per)` picks between them. The small line is kept short (user request): "ไตรมาส 4/2569 · อัปเดต 3 พ.ย. 69" (`fiscalQuarter`, Oct–Dec = Q1; `fmtThaiDateShort` of `window.ACP_SYNCED_AT` = max `synced_at`, never the browser's date). History periods show "ข้อมูลย้อนหลัง · ไตรมาส …/… · บันทึก …" (`parseThaiStamp`). The full date and time go in the badge `title` and `#methodModal`. The report's live period label ("ข้อมูลล่าสุด ณ …") and `#methodModal` use the same date. The sheet column `ข้อมูล ณ วันที่` is not used (it was wrong: 31/10/69 Q1 on FY2569 data). `document.title` and `#hdrFY` are set in `ACPDash.start()`; the legacy print title uses `window.__viewFY`. Don't hard-code a fiscal year in UI text. `#printArea` serves two print modes: `.legacy` (annual-table print) and `.report` (report pages). Scope any print-area table style to `.legacy`, because an id selector beats `.rp-tbl` and breaks report pages.
- Share preview (LINE/Facebook) uses Open Graph tags in `<head>` pointing to `og-image.png` (1200×630); tab icons are `favicon.png` / `apple-touch-icon.png`. These three PNGs are whitelisted in `.gitignore` (which ignores `*.png`). They were rendered with headless Chrome from the embedded RAOT logo. LINE caches previews, so a changed image may take a while to appear for links that were already shared.

- `#methodModal` ("นิยามและวิธีคำนวณ", opened by any `.method-link` — in the sidebar credit card and the footer source line, bound once in `initMethodModal()` in the loader block) documents the calculation rules above. Keep it in sync when a rule changes. The ดีมาก/ดี/พอใช้/ต้องปรับปรุง thresholds are **not** stated (they come from sheet formulas the user hasn't confirmed).
- Data-quality checks live in Apps Script, not on the public site: `runDataChecks()` (menu **ตรวจสอบความถูกต้องของข้อมูล**, and run automatically inside `syncToSupabaseLogged()` as a warning only) writes issues to the sheet `ตรวจสอบข้อมูล`, which is not in `SYNC_SHEETS`. It also flags projects whose `ร้อยละความก้าวหน้าเทียบแผนสะสม` is blank on every row (Nov 2026: 5 projects showed "-" on the dashboard while the sheet's status formula said ต้องปรับปรุง).
- Unit report forms → `ผลการดำเนินงาน` (Apps Script, replaces per-cell IMPORTRANGE that broke when units inserted rows). Each division has one Google Sheet with one tab per project. Their links are listed in the sheet `แหล่งแบบฟอร์ม` (column B). `parseFormTab()` finds everything by label, never by position: `รหัสโครงการ` / `งบจัดสรร` in the header; the sections `ติดตามการดำเนินงานตามตัวชี้วัด` / `ติดตามการดำเนินงานตามแผน`; the แผน/ผล label column, then V = label + 13 and W = label + 14; the plan-section row `รวม` and `รวมงบประมาณโครงการ`. KPIs are matched by a `รหัสตัวชี้วัด` column in the form, which `writeKpiCodes()` fills once in order (Output before Outcome, from `ตัวชี้วัดโครงการ`) and reports in `ผลการดึงแบบฟอร์ม` so names can be checked. `importFromForms()` writes only G เป้าหมายสะสม, H ผลจริง, J ร้อยละความก้าวหน้าเทียบแผนสะสม (first row of the project), P งบประมาณจัดสรร and Q เบิกจ่าย. Cells it can't fill keep their existing formula or value, and each one is listed in the report. The columns I/K/R and the L–N statuses stay as sheet formulas. It runs from a separate menu before archiving and doesn't sync by itself. Neither new sheet is in `SYNC_SHEETS`. The menu **ใส่สูตรมาตรฐานในแบบฟอร์มหน่วยงาน** (`standardFormulasMenu` → `standardizeForms` → `standardizeFormTab`) first does a dry run into `ผลการดึงแบบฟอร์ม`, then asks before writing. It creates one `REPORT_MONTH` named range per file (hidden tab `_ตั้งค่า`, `=MOD(MONTH(EDATE(TODAY(),-1))-10,12)+1`; type 12 over it after year-end). It writes only columns V–Y: per item V (plan up to `REPORT_MONTH`; "ร้อยละ" averages), W (not due → 0, ahead of plan → 1, clamped −1..1, × weight F only in the plan section when F is a number), X = `N(G)`, Y; and section totals (KPI groups = mean of due items; the plan total = weighted, counting only rows with F > 0). Each month's plan and result cells are never touched; other cells in V–Y keep their formula or value. It skips, and notes in the report: rows whose next row isn't ผล, items with extra result rows (province splits like 010308), V formulas that reference other rows (custom roll-ups), and "ไม่เกิน" KPIs with a non-numeric target. "ไม่เกิน" items get a ceiling formula. It also warns about weights that don't sum to 100% per activity, weights > 1, and "ร้อยละ" items whose monthly plan is far below the target. Tested on a copy of a real division file (`ฝสผ. 2.xlsx`, 10 tabs, 72 items).
